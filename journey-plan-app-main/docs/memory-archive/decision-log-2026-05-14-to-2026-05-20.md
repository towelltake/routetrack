### 2026-05-20 — Day-spread cramming fix (global-span cost on Time dimension)

- **Phase change:** none. Solver objective fix.
- **Trigger:** User flagged Plan #44 (real Towell dataset): Nizwa, Rumais, Salalah salesmen were using only 2-6 days of their 20 available working days, packing 27-37 visits into single days that ran 23-40 hours of total time. Specific examples — Nizwa Wed 2026-05-27: 27 visits, 1419 min total; Rumais Sun 2026-05-24: 37 visits, 1801 min (33h); Salalah Sun 2026-05-24: 37 visits, 1389 min. Other days completely empty even though same salesman's working window made them available.
- **Root cause (proven via [test_day_spread_repro.py](sidecar/tests/test_day_spread_repro.py)):** The encoded VRP objective had no spread incentive. Sum of (arc + per-vehicle fixed cost 90 + soft overflow penalty) — and for the no-overflow case (most weeks of light regions), arc and overflow are identical regardless of distribution, so the only differentiator is fixed cost. Cramming into N days costs N×90 fixed. Spreading to N+M days costs (N+M)×90. Solver was being optimal w.r.t. an incomplete model. For the overflow case, soft penalty (100/min) does dominate fixed cost in theory but GLS gets stuck in PATH_CHEAPEST_ARC's initial cram-heavy solution within the 300 s/week budget on real-data scale.
- **Shipped:**
  - [vrp.py](sidecar/sidecar/solver/vrp.py) — new constant `_SPAN_COST_COEFFICIENT = 10`. Added `time_dim.SetGlobalSpanCostCoefficient(10)` after the soft upper-bound loop. Penalises the BUSIEST day's total time across all (salesman, day) vehicles in the per-week solve. With 10× coefficient: a 100-min imbalance in the max-day load costs 1000, vs the 90 fixed cost saved by collapsing two days into one — so spread always beats cram unless drive penalty makes spread strictly worse.
  - [tests/test_day_spread_repro.py](sidecar/tests/test_day_spread_repro.py) — 2 new tests:
    - `test_solver_spreads_light_load_across_available_days`: 30 freq=4 customers, 30-min facetime, 5-min drive. Asserts each of 4 weeks uses ≥3 of 5 available days, no day >12 visits.
    - `test_solver_avoids_overflow_when_empty_days_available`: same but 60-min facetime so cramming causes overflow. Asserts no day's total time exceeds 540-min window.
  - [scripts/debug-day-spread.py](scripts/debug-day-spread.py) — audit script that lists per-salesman day usage + per-day load detail for Nizwa/Rumais/Salalah specifically. Used to quantify the bug; kept as a debugging artifact for the next time a regional balance question comes up.
- **Why GlobalSpanCost not lower fixed-cost:**
  - Fixed cost reduction (90 → 5) would help spread but also let the solver open a fresh day for a single short customer when adjacent days have slack — fragmenting low-load weeks.
  - Global span penalty is direct: "the busiest day should be as light as possible." Doesn't fight legitimate single-customer-day cases (where max IS just that one customer, span = facetime, low penalty).
  - For low-load weeks (1-2 customers): span is tiny regardless, no over-spreading.
  - For high-load weeks: spread to all available days because reducing max-day pays off.
- **`resequence_day.py` not touched:** single vehicle, single day. Global span is trivially the salesman's own span — no spreading possible.

  - `pnpm typecheck` n/a (no TS surface changed).

### 2026-05-20 — Cluster-aware tiebreak in cycle_assignment (week selection)
- **Phase change:** none. Refinement to the week-assignment layer.
- **Trigger:** User flagged a gap: the VRP already bundles same-cluster customers onto the same day via the 90-min per-vehicle fixed cost, but `cycle_assignment.py` (which picks WHICH WEEK each customer falls in) was geography-blind. Two freq=1 customers in the same (salesman, area) cluster could scatter into different weeks, forcing the salesman to make a fresh trip to the area each week instead of bundling into the cluster's "natural" week.
- **Shipped:**
  - [sidecar/sidecar/solver/cycle_assignment.py](sidecar/sidecar/solver/cycle_assignment.py) — new `_cluster_key(c) = (pinned_salesman_id, area)` when both are set. Per-iteration `cluster_visits[(s, area)] = [count per week]` heat tracker (binary signal: "salesman already touching this cluster this week, yes/no"). Lexicographic tiebreak across all flexible-frequency branches:
    - freq=1: pick `min((hot[w], week_load[w]))` instead of just `min(week_load[w])`.
    - freq=2: pick the {W0,W2} vs {W1,W3} pattern whose pair-sum of hot is larger; load-balance only on heat tie.
    - freq=3: sort by `(hot[w], week_load[w])`, take first 3.
    - freq>4 extras: same lexicographic key for the remainder distribution.
    - freq=4: unchanged (all weeks).
    - Customer with no pinned_salesman_id OR no area → `cluster_key = None` → `hot = [1,1,1,1]` → fully equivalent to pre-change load-balance.
  - **Effective salesman = `pinned_salesman_id`** (no new field needed). `planner.ts` already coalesces `assignedSalesmanId` into `pinnedSalesmanId` before sending — so cycle_assignment automatically sees the post-Phase-7b sticky assignment.
  - [sidecar/tests/test_solver.py](sidecar/tests/test_solver.py) — 4 new tests:
    - `test_cycle_freq1_bundles_into_hot_week_when_cluster_already_active`: freq=2 anchor takes {W0,W2}; freq=1 cluster-mate forced into W0 or W2 even though W1/W3 are load-lighter.
    - `test_cycle_freq2_pair_in_same_cluster_aligns_on_one_pattern`: two freq=2 customers in same cluster pick the same {W0,W2} or {W1,W3} pattern instead of one-each (old behavior).
    - `test_cycle_no_cluster_bundling_without_salesman_pin`: four freq=1 customers with no pin still spread one-per-week → behavior unchanged for un-pinned data.
    - `test_cycle_different_salesmen_do_not_share_cluster_heat`: two salesmen owning subsets of the same area name don't cross-pollute each other's heat (cluster key is (salesman, area), not just area).
- **Why binary heat, not weighted facetime:**
  - The cost we're avoiding is "an extra drive to the cluster," which is the same whether the salesman makes 1 extra visit or 5. Weighting by facetime would let a 200-min hypermarket in W0 outweigh five 15-min grocers in W2 — the wrong signal. Binary `was_there/wasn't` matches the physical cost.

### 2026-05-18 (latest, urban calibration) — OSRM duration multiplier; cache cleared
- **Phase change:** still Phase 6. Closes a quality issue surfaced after dev E2E.
- **Trigger:** spot-check of 30 cached cells vs fresh OSRM calls (same coordinate pairs) revealed a systematic bias:
  - Short urban legs (<5 min cached): OSRM was 30-55% faster (e.g. 38s → 16s, 192s → 109s, 406s → 279s, 629s → 296s).
  - Medium trips (10-30 min): usually within 10%, sometimes OSRM slightly slower.
  - Long highway trips (>30 min): within 5%.
  - Aggregate: median -3.4% duration, mean -7.6%; 7 of 30 cells had >25% delta — all on short legs.
- **Why:** OSRM's stock `car.lua` profile uses idealized free-flow times — no turn delays, no stop-sign idle, no historical traffic. Google Distance Matrix bakes those in. For dense urban customer clusters this means the solver would fit ~30% more visits per day than is physically realistic — a problem the existing 10-min daily slack in `vrp.py` cannot absorb.
- **Decision: 3-band urban calibration in `sidecar/maps/osrm_matrix.py`.** Per-cell duration multiplier applied at the OSRM-client layer, before the value is returned to the planner:
  - **< 600s (urban)** → ×1.40
  - **600-1800s (suburban / inter-city)** → ×1.15
  - **> 1800s (highway)** → ×1.00
  - Tunable per-deployment via env: `OSRM_URBAN_MULT`, `OSRM_SUBURBAN_MULT`, `OSRM_HIGHWAY_MULT`. Setting all three to 1.0 disables calibration entirely — useful for A/B against the cached Google data or for re-calibrating after a real-world week.
  - **Distance values pass through unchanged** — OSRM's road geometry is accurate; only the time estimate needed adjustment.
- **What didn't make it:**
  - **Custom Lua profile** — would address the root cause but is out of scope for v1 and requires Lua expertise to maintain.
  - **Working-hours-budget cut** — too crude; would penalize sparse plans the same as dense urban ones.
  - **Acceptance with no calibration** — would push the error onto field reps. Better to model it in the plan.
- **Cache wiped after calibration landed.** The existing `distance_cache` held 67,834 rows of Google-derived values from earlier pre-OSRM runs. Cache reads bypass `osrm_matrix.py` entirely, so the calibration would have had zero effect on the next plan until those rows were either evicted or recomputed. Deleted all rows; next plan generation will refetch fresh from OSRM (with calibration applied) at zero API cost. `directions_cache` untouched (8 rows, Google polylines for route previews — unaffected by calibration).

  - **38/38 sidecar tests green** (35 + 2 new calibration tests + 1 updated to opt out of calibration explicitly).

### 2026-05-18 (late) — Single-pass VRP replaces k-means pre-clustering. Suggest Team Size gets target-util slider.
- **Phase change:** still Phase 5 shipped — these are quality improvements to the optimizer, no scope change.
- **Bug:** the morning's k-means pre-clustering caused systematic underutilization. Real-dataset symptoms (Plan #2 baseline with 11 salesmen against 532 customers): 12% of working days fully loaded but 36% under 4h, two Muscat salesmen at 0–55% util while customers were dropped as "could not fit". User pushed back hard: "how do the best apps do this?"
- **Architecture change:** dropped pre-clustering entirely. The k-means → match-cluster-to-salesman → hard-pin pipeline was a heuristic for problems too large for the solver — overkill for 500 customers × ~200 vehicles. Real production routing systems (Locus, OptimoRoute, Route4Me) hand the full problem to the solver. The OR-Tools VRP with area-eligibility constraints + disjunction penalty + per-vehicle fixed cost gives optimal load balance natively. `planner.ts:clusterCustomersToSalesmen` is dead code now; kept for reference, no longer called by `generatePlan`.
- **What worked (Plan #13, single-pass VRP, real Towell dataset 532 customers / 11 salesmen):**
  - **0 unassigned** (down from 3 lucky / 6–9 typical with k-means)
  - **64.3% of working days hit 8–9 hours** (up from 12.4% — 5× improvement)
  - **5.2% of days are <4 hours** (down from 36.3% — 7× improvement)
  - 1463 visits, 66.7% overall util, ~40s runtime
  - Trade-off: 31.8% of customers (169/532) see >1 salesman across the month (each week solved independently → each visit gets its locally-optimal salesman)
- **What did NOT work (tried and rejected this session):**
  - Capacity-aware load-balance pass on k-means clusters — moved heavy customers (LULU 90×8=720min, MAFH, Al Meera) away from their geographically-nearest cluster to "lighter" but distant clusters. Net effect: MORE unassigned (9 vs 3) because drive time exploded. Capacity-aware balancing fights the VRP.
  - Two-phase VRP (Phase 1 discovery → derive dominant salesman per customer → Phase 2 stabilize with derived pins). Conceptually clean (it's the standard "consistent VRP" pattern) but in practice the Phase-1-derived pins recreated the same overflow as k-means: heavy customers visited by 2+ salesmen in Phase 1 get force-pinned to one in Phase 2, which then can't fit them all. User: "this made it worse make it go back to only VRP and i'll set the salesman per customer in my upload template".
  - Multi-restart k-means (8 then 12 seeds) with load-weighted scoring then max-load scoring. Slight improvements but never matched Plan #13's unconstrained-VRP quality.
- **Decisions locked:**
  - **Single-pass VRP is the v1 algorithm.** No automatic salesman-customer pinning. User controls consistency via the `pinned_salesman_name` import column for relationship-critical accounts (~5-15% of customers).
  - **`buildNeededPairs` groups by area** (was: by pinned-salesman-cluster). Since any customer in area X can be routed through any salesman in X, the matrix needs complete intra-area coverage — not intra-cluster. Floating customers (no area + no pin) use k-NN as before.

  - **VRP daily capacity gets +10 min slack** in `vrp.py:165-175`. Reflects operational reality (a rep can run 5-10 min past 17:00 to finish a visit). Without it, a customer whose visit would end at 17:01 is rejected as "could not fit". Tunes the cliff edge of the capacity constraint without inflating headcount.
  - **Per-vehicle fixed cost stays at 90 min** in `vrp.py`. Discourages opening a day for <3 customers. Combined with single-pass VRP this produced the 64% full-day result.
  - **`Suggest Team Size` gets a `targetUtilizationPct` slider** (default 85%) in PlanScreen + new field in TeamSizeTemplate (shared TS + Pydantic). Algorithm stops growing the team once avg util drops below the target. Lets the user explicitly trade coverage for utilization. Implementation in `sidecar/solver/team_sizing.py:_utilization_pct` + early-break in `_solve_for_area`.
