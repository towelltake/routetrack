Pre-build inspection of the embedded 32×32 frame on the installed v0.12.3 .exe showed dithered green noise — diagnostic that proved this was an encoder bug, not a Windows shell-cache issue or a source-asset issue.

  - Hand-rolled PNG-in-ICO writer in `build-icon.cjs`. Embeds the source PNGs (produced by `sharp` at sizes 16/24/32/48/64/128/256) directly as PNG-format frames inside the ICO container — a format Windows Vista+ supports natively for every frame size. No DIB encoding surface to get wrong, alpha preserved. Drops the `to-ico` dep entirely (~600 LOC of transitive deps removed).
  - Regenerated `app/build/icon.ico` (158 KB, down from 352 KB — PNGs compress better than DIBs). 7 frames verified via directory dump (`reserved=0, type=1, count=7`, all `bpp=32, format=PNG`) and frame extraction of the 32×32 showing the brand illustration (businessman + chart on dark navy).

Aligns with CLAUDE.md §5 "no premature abstraction."

Windows aggressively caches icons on a per-.exe-path basis, so any stale broken icon survives a reinstall to the same path unless the cache is explicitly cleared — Explorer restart + `iconcache_*.db` deletion is the standard procedure.

### 2026-05-22 — Orphan child-process fix (`killTree`)

- **Phase change:** still Phase 12. Defensive plumbing only.
- **Trigger:** User: *"i just closed the installer version and the sidecar.exe was still running we need to fix that for dev and installer."* Reproduces what the morning smoke test already documented in both dev and prod — the previous launch's leftover Python sidecar blocks OSRM startup on the next launch, surfacing as the "OSRM down" badge until the orphan is killed manually.
- **Root cause:** `stopSidecar()` and `stopOsrm()` both called `proc.kill()` which on Windows is `TerminateProcess` on the immediate process handle. Doesn't propagate to descendants. Two shapes both leak:
  - **Prod:** PyInstaller's onefile `sidecar.exe` is a bootloader that re-spawns the real Python interpreter as a separate child process.
  - **Dev:** `cmd /c uv run python -m sidecar.main` produces a chain `cmd.exe → uv → python` — the Node pid is `cmd.exe`, the Python interpreter is two layers down.
- **Shipped:**
  - [app/src/main/processTree.ts](app/src/main/processTree.ts) — new sync `killTree(proc)` helper. On Windows: `spawnSync('taskkill', ['/T', '/F', '/PID', pid], {windowsHide: true, stdio: 'ignore'})`. `/T` walks the descendant tree, `/F` is force-terminate. Falls through to `proc.kill()` afterward as a no-op safety. On POSIX: just `proc.kill()` — fork+exec children inherit the signal via the process group on Linux/macOS, and PyInstaller's POSIX bootloader traps + propagates.
  - [app/src/main/sidecar.ts:stopSidecar](app/src/main/sidecar.ts) — replaced `proc.kill()` with `killTree(proc)`.
  - [app/src/main/osrm.ts:stopOsrm](app/src/main/osrm.ts) — same. Kept symmetric even though current `osrm-routed` builds don't spawn workers — it's the same class of problem and the cost of the extra `taskkill` call is negligible.
- **Why sync (not async):** `before-quit` is sync; making it async would require `event.preventDefault()` + a manual `app.exit()` after awaiting, which is a more fragile pattern. `spawnSync` blocks the quit just long enough (~50ms in practice) for the tree to reap, then `closeDb()` runs against a quiet system.
- **Why no new dep:** considered `tree-kill` npm package, rejected — `taskkill` is built into Windows since XP, adding a transitive dep for one Windows-only sync call would violate CLAUDE.md §5 "no premature abstraction."
- **Verification:**
  - `pnpm --filter @journey/app typecheck` — clean.
  - Manual verification on dev/installer pending the next quit (small, mechanical fix; the failure mode is observable in Task Manager).
- **What this does NOT cover:** if Electron itself is hard-killed (SIGKILL on the Electron process, power loss, OS reboot, force-end-task on `electron.exe`), `before-quit` never fires and orphans still survive. That's unsolvable from inside the parent; a future enhancement could be a small "previous run still has orphans" check at startup that runs `taskkill /F /IM sidecar.exe /T` + `taskkill /F /IM osrm-routed.exe /T` before `startOsrm` — but that's an aggressive sledgehammer (would kill other users' instances on shared machines) and we don't need it yet.
- **Net code:** 1 new file (32 LOC), 6 lines changed across 2 files (2 imports + 2 stop fns rewritten in 2 lines each).
- **Shipped:** `installer/JourneyPlanApp-Setup-0.1.0.exe` rebuilt 2026-05-22 21:29 (745 MB / 781,337,104 bytes) via `pnpm dist`. electron-builder reused the existing `sidecar.exe` (correct — no Python code changed).
